Обобщения в C#: иерархии классов, структуры, делегаты, интерфейсы и методы расширения


1 Название и описание библиотеки

DataFlow.Core — это переиспользуемая библиотека классов, предназначенная для унифицированного хранения, фильтрации и потоковой обработки однотипных данных с использованием обобщенных механизмов языка C#, обеспечивающая строгую типобезопасность без дублирования исходного кода.

2 Предметная область и типы домена

Для реализации демонстрационного сценария выбрана предметная область «Складской учёт». В проекте DataFlow.Demo созданы следующие типы домена:
 Product : Реализует маркерный интерфейс IEntity для поиска элементов в репозитории, а также обобщенный интерфейс IComparable<Product> для сравнения объектов по свойству Price (цене).
 Customer : Реализует только интерфейс IEntity, представляя сущность, не участвующую в операциях сортировки и поиска экстремумов.
 Animal & Dog: Вспомогательная простая иерархия классов, предназначенная исключительно для демонстрации механизмов ковариантности контрактов.

4 Разбор по шагам: ответы на обязательные вопросы


Шаг 0 Подготовка решения

 Зачем в решении два проекта, а не один? Чтобы отделить переиспользуемую инфраструктурную логику DataFlow.Core от конкретной бизнес-логики приложения DataFlow.Demo. Это исключает связывание ядра с типами домена.
 Консольный проект DataFlow.Demo не сможет использовать типы из сборки DataFlow.Core, что приведет к ошибкам компиляции при попытке обратиться к любому классу ядра.
 Почему проект библиотеки нельзя запустить, а консольный — можно? Библиотека classlib компилируется в .dll и не имеет точки входа метода Main. Консольное приложение компилируется в исполняемый файл .exe и содержит точку входа.

Шаг 1 Обобщённый базовый класс Buffer<T>

1 Поле items с модификатором protected доступно внутри базового класса и его наследников например, LabeledBuffer, но скрыто от внешнего кода. private сломал бы наследование в Шаге 2, а public нарушил бы инкапсуляцию.
2 Модификатор readonly запрещает повторно инициализировать  саму ссылку на объект List<T> после создания буфера, но не запрещает модифицировать внутреннее состояние списка.
3 TryAdd возвращает bool. Это проектирование под полиморфизм. Базовый класс закладывает контракт потенциального отказа в будущем, который реализуется в GuardedBuffer.
4 Что произойдет, если убрать ключевое слово virtual? Наследники не смогут переопределить метод TryAdd, что сделает невозможным динамический полиморфизм.
5 Чем new() отличается от new List<T>()?  Конструктор new() автоматически выводит тип из объявления поля, исключая его дублирование в коде.

Шаг 2 Наследование с фиксацией типа — LabeledBuffer

1 LabeledBuffer закрывает обобщение, жестко фиксируя T = string, превращаясь в обычный специализированный класс. GuardedBuffer<T> оставляет generic-параметр открытым, передавая его дальше, сохраняя универсальность для любых типов.
2 Почему PrintAllUpper() невозможно было написать в Buffer<T>? Потому что в Buffer<T> тип T неизвестен. 
3 Что случится, если попытаться объявить LabeledBuffer<int>? Возникнет ошибка компиляции, так как класс LabeledBuffer спроектирован как необобщенный и не имеет параметров типа в своем объявлении.
4 Смог ли бы LabeledBuffer хранить числа, если бы он наследовался от Buffer<object>? Да, смог бы. Однако это полностью разрушило бы строгую типобезопасность, потребовало бы явного приведения типов и привело бы к потенциальным ошибкам InvalidCastException во время выполнения.

Шаг 3 Переопределение с сохранением обобщённости — GuardedBuffer<T>

1 Почему проверка отказа стоит до вызова базового метода, а не после? Чтобы предотвратить несанкционированное попадание некорректного элемента в защищенное хранилище items. Если вызвать базу раньше, элемент уже запишется в список.
2 Что произойдет, если считать AcceptedCount до проверки результата базы? Если базовый класс в будущем отклонит элемент и вернет false, счетчик AcceptedCount увеличится ложно, нарушив инвариант класса.
3 Чем отличается поведение GuardedBuffer<int> и GuardedBuffer<string>, если код класса один и тот же? Код один, но предикаты фильтрации разные. Для int он может проверять x => x > 0, а для string — s => !string.IsNullOrWhiteSpace(s). Обобщенный класс делегирует эту специфику внешнему поведению через Func<T, bool>.
4 Почему нельзя вместо base.TryAdd(item) написать items.Add(item). Прямая запись нарушает принцип DRY и переиспользование кода. Если базовая логика добавления изменится, логика наследника сломается.
5 Что произойдет, если перенести условие отказа внутрь тела класса вместо параметра конструктора? Класс мгновенно потеряет универсальность.

Шаг 4 Обобщённая структура, делегат и метод

1 Чем struct отличается от class для вызывающего кода? Структура — это тип значения, размещаемый в стеке, и передаваемый по значению. Класс — ссылочный тип, передающий лишь ссылку на кучу.
2 Что выведет Console.WriteLine(record), если не переопределять ToString()? Будет выведено полное имя типа с метаданными generic-аргументов: DataFlow.Core.Record1[System.Double]`.
3 Как компилятор понял, что TResult равен string во втором вызове? Благодаря механизму вывода типов Type Inference. Компилятор проанализировал сигнатуру переданного лямбда-выражения (double c) => ... и обнаружил, что возвращаемое выражение имеет тип string.
4 Почему нельзя было реализовать преобразование отдельным методом ToFahrenheit и ToCategory без обобщения? Без обобщений нам пришлось бы писать уникальные методы для каждой новой комбинации типов, дублирование кода и лишая библиотеку абстракции.
5 Что произойдет, если убрать переопределение ToString() — увидит ли это проверяющий в выводе программы? Да, вместо понятных строковых данных вида °C: 20 в консоль выведутся системные имена типов, что прямо нарушит критерии проверки.

Шаг 5 Обобщённые интерфейсы и ограничение типа

1 Что произойдет, если убрать where T : IEntity и попытаться написать тело методов? Код репозитория перестанет компилироваться. Компилятор не позволит выполнить операцию item.Id, поскольку для произвольного типа T наличие свойства Id не гарантировано.
2 Почему ограничение проверяется компилятором, а не во время выполнения? Это гарантирует безопасность на этапе сборки, исключая возникновение критических ошибок типов в Runtime, и повышает производительность.
3 Что означает T в GetById и почему это не то же самое, что Nullable<T> для значимых типов в контексте обобщений без ограничений struct/class. Синтаксис T означает default-значение. Если T окажется структурой, Nullable<T> — это обертка Struct, а для ссылочного типа T — это просто аннотация для статического анализатора компилятора.
4 Что произойдет, если добавить в IContainer<out T> метод void Put(T item)? Произойдет ошибка компиляции CS1961. Ключевое слово out делает интерфейс ковариантным, накладывая ограничение: тип T может находиться исключительно на выходных позициях.

Шаг 6 Реализация репозитория на общем списке

1 Почему ограничение where T : IEntity нужно указывать и на интерфейсе, и на реализации? Класс InMemoryRepository<T> реализует IRepository<T>. Чтобы сигнатуры типов совпали и класс имел право обращаться к item.Id, ограничения должны быть полностью идентичными.
2 Что означает return default для ссылочного типа и для int? Для ссылочного типа это вернет null, а для значимого типа int это вернет численное значение 0.
3 Что будет, если вернуть null при возможном типе-структуре и какой код ошибки выдаёт компилятор? Компилятор выдаст ошибку CS0403: Не удается преобразовать значение NULL в параметр типа T, так как он может быть типом значения, не допускающим значение NULL. Поэтому необходимо использовать универсальное ключевое слово default.
4 Почему поле items здесь private, а в Buffer<T> было protected? Класс InMemoryRepository объявлен как финальный для своей ветки архитектуры и не предполагает наследования от себя. Полное сокрытие поля защищает внутреннее состояние коллекции.

Шаг 7 Ковариантность: класс против интерфейса

1 Почему IContainer<Animal> принимает Container<Dog>, а Container<Animal> — нет? Интерфейс IContainer<out T> объявлен как ковариантный за счет модификатора out, гарантируя безопасность вывода объектов. Сам конкретный класс Container<T> является инвариантным — для компилятора типы классов с разными аргументами абсолютно несовместимы.
2 Что мы теряем, объявив out T? Мы полностью потеряли право передавать тип T в качестве входящих аргументов в методы данного интерфейса.
3 Зачем класс помечен sealed, если ковариантность объявлена на интерфейсе? Модификатор sealed запрещает наследование класса. Если бы класс можно было унаследовать, то наследник мог бы обойти ограничения контракта ковариантности и нарушить безопасность типов.
4 Приведите пример, где IContainer<Animal> дал бы больше пользы, чем Container<Animal>. В методах обработки коллекций. Например, метод void ProcessZoo(IEnumerable<IContainer<Animal>> zoo) сможет без ошибок принять коллекцию специализированных контейнеров собак List<Container<Dog>>.

Шаг 8 Методы расширения

1 Что произойдет, если заменить параметр IEnumerable<T> на List<T>? Что именно перестанет работать? Метод потеряет полиморфную гибкость. Он перестанет вызываться на массивах , результатах выборки LINQ , хэш-таблицах и любых кастомных коллекциях.
2 Зачем в FindMax ограничение where T : IComparable<T> — что именно не скомпилируется без него? Строка item.CompareTo(best!). Без явного контракта IComparable<T> компилятор выдаст ошибку, так как у произвольного типа T метод сравнения отсутствует.
3 Почему метод нельзя заменить на готовый Max() из LINQ? По условию спецификации метод не должен генерировать исключений на пустых наборах данных, в то время как стандартный LINQ Max() выбрасывает InvalidOperationException на пустой коллекции.
4 Чем return default отличается от return null в вашем случае и почему это видно по выводу? На пустой коллекции строк метод вернет null, а на пустой коллекции чисел он вернет значение по умолчанию 0. Прямой return null привел бы к ошибке компиляции для числовых коллекций.
5 Что означает best! и почему без него не собирается? Знак ! — это null-forgiving оператор. Он сообщает компилятору в контексте Nullable Reference Types, что разработчик гарантирует отсутствие null в данной точке выполнения, отключая предупреждение анализатора.

Шаг 9 Предметная область и IComparable

1 Что произойдет, если удалить Id из Product? Класс нарушит контракт интерфейса IEntity, что приведет к невозможности компиляции и использования продуктов внутри InMemoryRepository<Product>.
2 Зачем CompareTo принимает Product, а не просто Product? Требование интерфейса IComparable<T>. Метод обязан корректно обрабатывать входящие параметры, которые могут быть равны null.
3 Что будет, если CompareTo будет возвращать 1 всегда? Нарушится математический закон транзитивности сравнения. Любые сортировки и алгоритмы поиска экстремумов начнут вести себя непредсказуемо и выдавать ошибочные результаты.
4 Как изменится вывод PrintAll, если убрать переопределение ToString()? Вместо детальной информации о товарах в консоль выведется монотонное имя типа: DataFlow.Demo.Product.
5 Почему Customer не реализует IComparable, а Product реализует? Сортировка клиентов по умолчанию не имеет однозначного бизнес-смысла в рамках данного склада, в то время как товары обладают явным критерием для сравнения — Price.

Шаг 10 Единый сценарий

1 Почему OutputEncoding выставлен первой строкой, а не где-то позже? Чтобы гарантировать корректную кодировку UTF-8 для всех последующих потоков вывода в консоль ОС Windows, предотвращая появление некорректных символов в самом начале работы программы.
2 Что в этом выводе доказывает, что GuardedBuffer<T> универсален, а не работает со строкой случайно? Тот факт, что в одном и том же сеансе работы буфер успешно и независимо обработал фильтрацию как числовых значений, так и текстовых.
3 По какой строке вывода видно, что счётчики экземпляров независимы? По строке вывода: Счётчики независимы: numbers.AcceptedCount = 2.
4 Найдите в выводе строку, где тип значения Record изменился с double на string. Как это связано с одной сигнатурой метода? Строка: double → string: Категория: тепло. Это демонстрирует работу generic-метода Map<T, TResult>, способного динамически выводить и возвращать разные типы данных на основе переданного делегата преобразования.
5 Что покажут строки про пустой List<int> и почему это не ошибка? Выведется 0. Это штатное поведение системы, обусловленное тем, что значением по умолчанию для типа int в среде .NET является ноль.

Шаг 11 Три ожидаемые ошибки компиляции

1 Почему ошибка 1 возникает для класса, но не возникает для интерфейса? Классы по умолчанию инвариантны. Интерфейсы же могут быть ковариантными при использовании ключевого слова out, разрешая такое приведение.
2 Что изменится в ошибке 2, если заменить out T на in T? Интерфейс станет контравариантным. Ошибка на методе Put(T item) исчезнет, но компилятор выдаст новую ошибку на методе T GetItem(), так как возвращать тип in T станет запрещено.
3 Какие ещё типы нельзя подставить в InMemoryRepository<T> и почему? Любые типы, которые не реализуют интерфейс IEntity, так как они нарушают generic-ограничение where T : IEntity.
4 Почему компилятор ловит все три ситуации до запуска программы? Благодаря статической типизации языка. Компилятор выполняет полный семантический анализ исходного кода до этапа генерации IL-кода.
5 Что означает принцип проверка на этапе компиляции для цены ошибки в разработке? Это минимизирует стоимость исправления дефектов архитектуры. Ошибка обнаруживается мгновенно на компьютере разработчика, не доходя до этапов тестирования и конечных пользователей.

6 Три ожидаемые ошибки компиляции


Ошибка 1 Инвариантность обобщенного класса

 Код ситуации: Container<Animal> box = new Container<Dog>(new Dog { Name = "Шарик" });
 Код ошибки: CS0029
 Текст ошибки: Не удается неявно преобразовать тип "Container<Dog>" в "Container<Animal>".
 Причина: Обобщенные классы в C# строго инвариантны. Несмотря на то, что Dog унаследован от Animal, типы Container<Dog> и Container<Animal> не имеют родственных связей.

Ошибка 2 Нарушение правил ковариантности контракта

 Код ситуации: внутри public interface IProbeContainer<out T> объявлен метод void Put(T item);
 Код ошибки: CS1961
 Текст ошибки: Недопустимое отклонение: Параметр типа T должен быть контравариантно допустимым на IProbeContainer<T>.Put(T). T является ковариантным.
 Причина: Ключевое слово out делает интерфейс ковариантным, накладывая жесткое обязательство: использовать параметр T только как возвращаемое значение. Передача T во входные аргументы грубо нарушает это правило.

Ошибка 3 Нарушение ограничений generic-параметров типа

 Код ситуации: var repo = new InMemoryRepository<string>();
 Код ошибки: CS0311
 Текст ошибки: Тип string не может быть использован как параметр типа T в универсальном типе или методе InMemoryRepository<T>. Нет преобразования неявной ссылки из string в IEntity.
 Причина: Класс InMemoryRepository<T> имеет строгое ограничение where T : IEntity. Системный тип string не реализует интерфейс IEntity, поэтому компилятор блокирует сборку.
